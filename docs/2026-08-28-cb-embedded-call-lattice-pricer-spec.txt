# 转股权定价 v2 —— 把发行人强赎决策做成内生变量(spec)

状态: draft, 未评审, 未进 proposal_gate。本文件只是工程设计, 不是研究方向的正式立项。
2026-08-29 已在 dgx 真实仓库数据上跑过第 7 节验收标准, 结果见本文件末尾
"9. 真实数据验收结果(2026-08-29)"。代码仍未接入 verifier.py, 未改变
current.yaml 记录的任何 truth。
背景来源: `study/options-market-structure.txt` 第七节、`study/diagnose_implied_vs_realized_vol.py`
产出的 `study/implied_vol_diagnostic/REPORT.txt`、`~/projects/knowledge` 里
`可转债有自己的结构` / `转债条款是发行人与持有人的博弈` / `cb_call表不能当强赎标记` 几条笔记
(dgx 与本机 2026-08-27~28 的分析, 未进本仓库版本控制)。

## 0. 一句话

现在的 `strategies/cb_arb/cb_pricer.py` 把"公司会不会主动收场"当成外部输入的
一个布尔量(`is_force_redeemed`), 不当成定价过程本身的一部分。本 spec 提议把这个
决策做成定价格子里内生算出来的东西, 而不是外部喂进来的开关。

## 1. 问题(已用数据证实, 不是猜测)

`study/implied_vol_diagnostic/REPORT.txt` 第 4b 节: 按"近 30 个交易日中 ≥15 日
S/K ≥ 1.3"(强赎条件的近似)分组, 未接近强赎条件的债 `(理论价-市价)/市价` 中位数
-5.44%, 已近似满足强赎条件的债则是 +17.00%, 落差 22 个百分点。机制解释:
`price_cb` 只在强赎**公告期内**(`is_force_redeemed=True`)才锁顶 103 元, 对"已满足
条件但尚未公告"的债, 仍按不可赎回的欧式 call 定价, 系统性给出偏高的理论价。
横截面排名把这批债排到最便宜一端买入, 随后强赎公告触发强制卖出。

诊断报告原话: "这条链路与波动率水平无关, 是条款建模缺失, 不是 vol 参数问题。"

## 2. 目标(v1, 本 spec 覆盖的范围)

把"发行人在满足条件时会主动收场"这件事,做成一个二叉格子(binomial lattice)里
逐节点内生比较、逐步倒推出来的结果, 而不是外部传入的开关。具体:

- 用二叉格子模拟正股价格路径(校准到跟现在一样的 `stock_vol` 输入, 不引入新的
  波动率来源)。
- 格子的每个节点携带一个真实状态:**过去 30 个交易日里, 有几天 S/K ≥ 1.3**
  (见第 3 节)。判断"当前是否处于强赎条件区间"时读这个真实计数, 不用单日
  触发或固定滞后天数这类近似。达到条件, 按发行人最优决策(收回 vs 放任转股,
  取对发行人更有利/对持有人更不利的那个)给这个节点的价值封顶。
- 现金流按 Tsiveriotis-Fernandes 拆分法分两条线折现: 会变成股票的部分按无风险
  利率折现(转股后信用风险不再相关), 会变成现金兑付的部分按信用利差折现(沿用
  `cb_pricer.py` 现有的 `DEFAULT_CREDIT_SPREAD_BP` 表, 不新增信用假设)。
- 从到期日倒推回今天, 得到理论价。

## 3. 共享工具: 强赎条件天数统计(单一权威实现)

**现状是三个地方各自猜一遍同一件事**, 这本身就是个要先治的问题:

| 位置 | 现在怎么判断"是否满足强赎条件" |
|---|---|
| `verifier.py` `_is_force_redeemed_on_date` | 读 `cb_call.parquet` 的 `ann_date`/`call_date` —— 已确认不可靠, 见第 4.1 节 |
| `study/diagnose_implied_vs_realized_vol.py` 的 `by_call_condition` 子样本 | 临时写在诊断脚本里的一次性判断逻辑, 没有沉淀成可复用的工具 |
| 本 spec 最初草稿 | 打算在格子里再简化成单日触发或固定滞后近似 —— **已否决**, 见下 |

三份各写各的, 迟早对不上, 而且没人知道哪份是对的。**本 spec 的前置交付物是
先做一个唯一的、正确的实现**, 其余两处(现有诊断脚本的临时逻辑、未来对
`is_force_redeemed` 的修复)都改成调用它, 不再各自维护一份。

- 新建 `strategies/cb_arb/call_condition.py`, 提供:
  - `trailing_trigger_count(ratio_series, window=30, threshold=1.30) -> int`:
    给一段 S/K 时间序列, 返回最近 `window` 个交易日里满足 `≥threshold` 的天数。
  - `is_call_eligible(ratio_series, window=30, threshold=1.30, required=15) -> bool`:
    包一层, `trailing_trigger_count(...) >= required`。
  - 参数(`window`/`threshold`/`required`)集中在这一个文件, 不散落在别处
    (呼应 `AGENTS.md` "状态码/枚举/参数一律进权威表" 的规矩)。
- **两种用法都走这一份实现**:
  1. **历史/截至今天**: 直接喂真实的历史 S/K 序列, 算出"以今天为估值日,
     是否已经满足条件", 用来替代 `verifier.py` 现在从 `cb_call.parquet`
     读出来的 `is_force_redeemed`(见第 4.1 节, 但本 spec 不改 `verifier.py`
     本身)。
  2. **格子内前向模拟**: 格子往前走的每一步, 把新模拟出的价格追加进这个
     计数状态, 用同一份 `trailing_trigger_count` 逻辑滚动更新, 而不是另写
     一套简化规则。
- **代价, 如实说清楚**: 把"过去 30 天里有几天满足"这个计数做成格子的真实
  状态, 意味着一个节点不再只有"价格"这一个维度, 还要带上"计数"这个维度
  (0-30, 离散、有限)。这会让格子比一个普通二叉树大, 但计数只有 31 种取值,
  是可控的、不是指数爆炸。实现时二选一, 在动手写代码前定:
  - **状态增强树**: 每个价格节点再叉出最多 31 种计数状态, 是普通二叉树的
    有限倍放大, 仍然是确定性倒推, 不依赖随机数。
  - **蒙特卡洛 + 最小二乘回归(Longstaff-Schwartz)**: 模拟一大批未来路径,
    每条路径自然带着自己的计数历史, 不需要人为限制状态数量, 但引入随机数
    带来的估计噪声, 且工程量比状态增强树大。
  两条路径都能给出正确答案, 选哪条是实现阶段的工程判断, 不是本 spec 要拍板
  的架构决定。

## 4. 明确排除的范围(不是本 spec 要做的事)

**下修(转股价下调)**: 不建模。原因: `cb_basic.conv_price` 是静态标量,
`cb_daily` 没有 `conv_price` 列(见 `data_inventory.yaml`), 仓库里没有下修事件
的历史记录, 无法验证也无法回测。做了也测不出对不对。

**回售**: 不建模。原因: `cb_basic` / `cb_call` 都没有 `put_date` / `put_price` /
回售金额字段(`knowledge/notes/转债的终点是强赎退市.md` "未解决的部分" 已确认),
数据层面完全看不见, 建了也是空转。

**逐券真实条款(触发比例、连续天数窗口)**: 不做逐券定制。数据仓库没有存这些
逐券合同细节, 只有 `interest_rate_explain` 这类票息条款文本, 没有强赎/下修
条款文本的结构化字段。v1 统一用 A 股转债市场公开的通行条款(股价连续 15/30 个
交易日 ≥ 转股价 130%, 集中在第 3 节那个工具的默认参数里), 在报告里明确标注
这是市场通行假设、不是逐券核实过的合同条款。

## 5. 前置依赖 / 风险 —— 动手前必须知道的两件事

### 5.1 `is_force_redeemed` 现在的数据源本身不可靠

`strategies/cb_arb/verifier.py` 里 `_is_force_redeemed_on_date` /
`_build_call_index` 直接读 `cb_call.parquet` 的 `ann_date` / `call_date` 判断
一只债是否已被强赎。`knowledge/notes/cb_call表不能当强赎标记.md` 已经用三条反证
说明这张表不能这么用: 997 只有记录的债里包含全部 338 只仍在存续的债(说明
`IS_REDEEM=='是'` 只是"含赎回条款", 不是"已被强赎"); 121 只存续中的债有非空
`call_date` 且之后正常交易了 2-4 年; `call_price` 全部落在 100-105 元, 强赎/
到期/回售三者赎回价长得一样, 区分不出事件类型。

**结论**: 本 spec 提议的新格子定价器, 判断"当前是否处于强赎条件区间"必须
用第 3 节的 `call_condition.py`、从正股价格历史直接算, 不能读 `cb_call.parquet`。

`is_force_redeemed` 这个外部布尔量本身要不要保留、`verifier.py` 里其余用到
`cb_call.parquet` 的地方要不要一并修——是独立于本 spec 的另一个问题, 本 spec
不处理, 只保证新代码不新增对这张表的依赖, 并且把"正确判断的方法"沉淀成第 3
节那份共享工具, 方便以后修 `verifier.py` 时直接复用。

### 5.2 回测台账目前不可依赖, 与本 spec 无关但会误导验收

`knowledge/maps/可转债研究.md` 记录了两个更严重、尚未修复的数据缺陷:
`退市转债的到期日字段被数据源改写`(已退市转债的 `maturity_date` 被数据源
改成了实际摘牌日, 不是合同到期日)和 `回测提前知道了转债哪天退市`
(824 笔交易里摘牌前 180 天内入场的是 0 笔, 疑似前视偏差)。knowledge 库原话:
"位移 7-34pp, 判定线 7pp。台账在修好之前不可依赖。"

**这意味着**: 本 spec 完成后, 如果直接跑现有的历史回测去验收"新定价器让
超额收益变好了没有", 结果不可信——回测台账本身还带着比本 spec 想修的 22pp
更大的已知偏差。第 7 节的验收标准因此**刻意不用完整历史回测的超额收益数字
做判据**, 只用不依赖回测台账的直接检验。若之后要用完整回测验收, 必须先等
上述两个数据缺陷修复, 这是另一条独立的修复工作, 不在本 spec 范围内。

## 6. 接口设计 —— 不动现有代码, 新增两条平行路径

`cb_pricer.py` 现在的 `price_cb` 是 `study/diagnose_implied_vs_realized_vol.py`
的参照实现(诊断脚本运行时会拿向量化版本跟它逐点对拍), 也是 `verifier.py`
当前在用的定价函数。不能原地改。

- 新建 `strategies/cb_arb/call_condition.py`(第 3 节), 唯一权威实现"是否满足
  强赎条件"这件事。
- 新建 `strategies/cb_arb/cb_pricer_lattice.py`, 提供 `price_cb_lattice(...)`,
  函数签名与 `price_cb` 对齐(同样吃 `CBSpec` + 估值日 + 正股价 + `stock_vol` +
  `risk_free_rate` + `credit_spread_bp`), 返回同样结构的 `CBValuation`, 新增
  `method="lattice"`。内部调用 `call_condition.py`, 不自己另写判断逻辑。
- 复用 `cb_pricer.py` 现有的 `bond_floor_pv`、`DEFAULT_CREDIT_SPREAD_BP`、
  `_years_between` / `_days_between`, 不重复实现。
- `study/diagnose_implied_vs_realized_vol.py` 里现有的 `by_call_condition`
  临时逻辑, 建议同步改成调用 `call_condition.py`(诊断脚本本身不算"红色边界",
  可以顺手改), 避免两份口径将来悄悄跑偏。
- `verifier.py` 不在本 spec 里切换定价函数。是否/何时切换, 待第 7 节验收
  结果出来后再决定, 且按项目规矩(`strategies/cb_arb/` 全部 `.py` 属红色边界)
  需要人工过一遍, 不能自动切。

## 7. 验收标准(不依赖回测台账)

1. **`call_condition.py` 自身先过一遍构造用例**: 手写几段"最近30天里恰好14天/
   15天/16天满足"的边界序列, 断言 `is_call_eligible` 在边界上下都判对; 再拿
   `cb_daily`/`stk_daily_qfq` 里几只已知历史强赎公告日在附近的真实券验证,
   `is_call_eligible` 应在公告日前若干交易日就已经判定为 True(公告通常滞后
   于条件满足, 这条能反过来验证工具做对了)。
2. **远离触发线时格子价应收敛到旧算法**: 抽样 S/K < 1.1 且距到期 > 1 年的
   观测, `price_cb_lattice` 与 `price_cb` 的理论价之差应在一个小的容差内
   (容差数值实现时定, 需报告实际分布, 不能只报"通过/不通过")。这条不成立
   说明格子实现本身有 bug, 不是模型分歧。
3. **临近强赎条件时应明显更低**: 用 `call_condition.py` 判定"已满足强赎条件"
   的观测, 比较 `price_cb_lattice` 与 `price_cb` 的理论价中位数——新算法应
   显著更低, 且向该组市场价方向移动。报告移动了多少, 不要求消灭全部 22pp
   落差, 但要说清楚消掉了多少、还剩多少、剩下的部分归因于什么(下修/回售
   未建模? 触发条件近似的误差? 别的?)。
4. 上述都是**一次性诊断脚本**产出的报告, 走 `study/` 现有的"只读、不进
   实验台账"规矩(参照 `.gitignore` 里 `study/*/` 那条注释的精神), 不新建
   `data/research_framework/` 下的记录。

## 9. 真实数据验收结果(2026-08-29)

脚本: `study/validate_cb_pricer_lattice.py`(dgx 上跑, 全量仓库数据, 每组抽样
150 条, `n_paths=4000`, 全程 21 秒)。产出目录 `study/lattice_pricer_validation/`
按 `study/*/` 惯例不进 git。

**组 B(已满足强赎条件, 本 spec 主要针对的问题): 缩小了约一半的落差, 没有
消灭**——

| 口径 | 数值 |
|---|---|
| 旧模型 (理论价-市价)/市价 中位数 | +20.70% |
| 新模型 (理论价-市价)/市价 中位数 | +10.54% |
| 缩小了 | 10.16 个百分点 |
| 新模型理论价相对旧模型的降幅中位数 | -7.13% |

跟 `study/implied_vol_diagnostic/REPORT.txt` 第 4b 节的 +17.00%(不同抽样口径,
量级一致)对照: 这次抽样基线更高一些(+20.70%), 但方向和量级都吻合, 说明
第 1 节那个问题是真实的, 且本 spec 的修法确实在起作用——只是只解决了一半左右。
**不宜据此宣称问题已修好, 只能说方向验证成立、幅度只对了一半。**

剩下这一半, 追过一层归因(2026-08-29): 按评级拆开看, 评级越高剩余缺口反而
略大(corr(rating_int, gap)=+0.12), **不支持"信用风险解释残差"这个方向**。
真正强相关的是 moneyness 和剩余期限(残差随两者显著变大), 指向本模块"满足
条件就假设立刻收场"这条假设本身还是过于简化——用 `cb_call.parquet` 的
`ann_date` 粗略核对, 从"价格历史首次满足条件"到那张表记的日期之间存在真实
的、双峰分布的时间差(一部分几天内就出现, 但相当一部分要数月到数年)。

**这条证据能确认什么、不能确认什么, 要分清楚**(2026-08-29 更正, 用户追问
"是没找到资料还是没公告"才发现最初的表述下早了结论): `cb_call.parquet`
每只债结构上只存 1 条记录(997 只债 997 条, 无例外), 不可能记录公司中途
可能反复发的"暂缓赎回"公告。所以上面这个时间差**不能**证明公司拖着不公告
——同样成立的另一种解释是公司其实一直在公告(反复暂缓), 只是这张表没存
那些中间记录。两个解释目前区分不开, 不是"下修/回售未建模"这个此前更早的
猜测那么简单就能定论的。详见 knowledge 库
`cb_call表结构上测不出满足条件后公司公告过几次.md`(`~/projects/knowledge/notes/`)
—— 这条本身测量方法还有明确局限(48%候选样本顺序核对不上, 且 `ann_date`
具体记的是哪个事件从未验证过), 不构成定论, 已如实记录, 是否要把"公告延迟"
做成 `price_cb_lattice` 的下一版功能, 需要单独立项(且需要先补一个公告文本
数据源才能真正区分上面两种解释), 不在本 spec 范围内。

**组 A(远离触发条件: S/K<1.1 且 T>1年) —— 大部分收敛, 但发现一条比 spec
写的更细的规律, 不是 bug**——

diff_pct 中位数 2.06%, 但 p95 到 7.58%、最大 13.42%, 比预想的"应该都很接近"
要分散。查了偏差最大的那批观测, 发现**偏差大小跟"剩余期限多长"强相关(相关
系数 0.17)、跟"当前离触发线多近"更强相关(相关系数 0.38)**——偏差最大的
几条清一色是剩余期限 4-6 年、moneyness 已经在 0.95-1.05 附近的债。

这不是实现 bug, 是一个真实的模型差异: 一只债今天虽然还没接近触发线, 但如果
名义剩余期限有 5 年、年化波动率 20-30%+, 累计起来这几年里"迟早涨到130%触发
强赎"的概率并不小。新模型会把这份"以后大概率被提前叫停"的可能性算进去,
压低长期期权的时间价值; 旧模型完全不考虑这件事, 假设期权能安稳活到名义到期日。
**"远离触发时应该收敛"这条验收标准, 严格说只对"剩余期限短"或"离触发线很远"
的债成立, 对"期限长 + 当前 moneyness 中等"的债, 两个模型本来就该有分歧,
分歧越大反而说明新模型在做它该做的事。** 这一条比 spec 原文写得细, 后续如果
要正式验收, 应该把组 A 的筛选条件再收紧(比如同时限制 T<3 年), 或者干脆把
"长期限+中等moneyness"单独拆一组来看, 不要跟"短期限"的债混在一起判断"是否
收敛"。
